# ISD91230 firmware map

The feeder's Nuvoton ISD91230 firmware is a stripped 64 KiB Cortex-M0 image.
This document separates facts visible in that image from physical functions
that still require a schematic, continuity measurement, or runtime trace.

Run the analysis from the repository root:

```sh
python3 research/analyze_isd91230.py /path/to/ISD91230.bin
python3 research/analyze_isd91230.py /path/to/ISD91230.bin --listing
```

The expected input is a private `ISD91230.bin` dump with SHA-256
`e8557cd0b4a601977cb53f2b42199c486e83ed7fa5187cc1f7d4f2b8ea20c201`.
The script uses Capstone for Thumb instructions and Rizin for recursive
function discovery. The peripheral names come from the ISD91200 Series
Technical Reference Manual, revision 2.9.

## Execution model

The reset vector enters `reset_handler` at `0x019c`. The C runtime then enters
`main` at `0x3678`, which initializes clocks, UART0, two timers, the watchdog,
GPIO, PWM, and analog sampling. Its foreground loop calls three tasks:

1. `periodic_power_task` at `0x3564` handles periodic sensing and a PA13/UART
   handshake.
2. `foreground_task` at `0x1538` feeds the M0 watchdog and processes UART
   commands every 20 timer ticks.
3. The routine at `0x1b84` prepares the M0 for low-power wait with `WFI`.

Timer0 increments four software counters at `0x200000e4` through
`0x200000f0`. Timer1 sets the work flag at `0x200000f4`. UART0's interrupt
handler places received bytes into the ring buffer used by the frame parser.
There is no active UART1 interrupt vector.

## ESP8266 bus

`process_uart_frame` at `0x0af8` calls the receiver at `0x1994`, validates the
CRC at `0x0d84`, then dispatches frame byte 3 through the switch table embedded
at `0x0b18`. The complete accepted command range is `0x00` through `0x13`:

| Type | M0 behavior established from control flow |
|---|---|
| `0x00`, `0x02`, `0x08`, `0x0a`, `0x0c`, `0x12` | Ignored as inbound commands |
| `0x01` | Save sequence number, schedule a status sample and type `0x02` reply |
| `0x03` | Store one 16-bit value in two related configuration fields |
| `0x04` | Store one 16-bit value in two related configuration fields |
| `0x05`, `0x06` | Store one 16-bit configuration value |
| `0x07` | Save sequence and argument, schedule the PB3/PB4 motion state machine |
| `0x09` | Save sequence and argument, schedule the opposite PB3/PB4 motion state machine |
| `0x0b` | Save sequence and dispense arguments, schedule the PB1/PB2 state machine |
| `0x0d` | Store the 12-byte configuration block used by motion and sensor thresholds |
| `0x0e` | Configure one of three timed output programs; subcommands 1 and 2 drive PA11 and PA12 |
| `0x0f` | Set the low-power-request flag |
| `0x10` | Set a flag whose consumer is not yet classified |
| `0x11` | Save an operation argument and sequence, then return GPIO PB6/PB7/PB8 state in type `0x12` |
| `0x13` | Save sequence and schedule the fixed type `0x14` response payload `00 04` |

The parser does not update a receive timestamp, reset a software countdown, or
feed the M0 watchdog. Command `0x01` also only saves its sequence and schedules
the reply. Therefore the regular status poll is not a conventional heartbeat
that keeps the M0 alive.

The M0 has a separate low-power path, but it is not driven by a missing UART
heartbeat. Command `0x0f` sets the enable flag at SRAM `0x20000042`.
`should_enter_low_power` requires that flag before it can leave the foreground
task and enter the low-power sequence. The current ESPHome implementation never
sends command `0x0f`.

On a periodic timer event, `detect_sensor_change` at `0x1a20` samples the
digital and analog inputs. A detected change makes `periodic_power_task` raise
PA13 and wait up to roughly 1,000 one-millisecond delays for any received UART
byte, then it returns PA13 to input mode. UART activity only shortens that wait;
reaching the timeout does not select the low-power path. When the sampled state
is stable, the function requests low power, but the separate command-`0x0f`
enable flag still gates entry. The electrical destination and purpose of PA13
are not established.

## GPIO and mechanisms

The firmware establishes these independent groups:

| Pins | Proven firmware use | Physical interpretation |
|---|---|---|
| PB1/PB2 | Bidirectional drive states in command `0x0b` | Dispenser motor control |
| PB3/PB4 | Bidirectional drive states in commands `0x07` and `0x09` | Outlet-door motor control |
| PB5 | Output raised for 5 ms before sampling PB6/PB7/PB8 | Optical sensor excitation |
| PB6 | Digital input returned as status byte 1; unused by the motor state machines | Optical food-level input; an assembled empty feeder reads 0, while covering the optical path changes it to 1 |
| PB7 | Digital input returned as status byte 2 and counted by command `0x0b` | Dispenser-wheel feedback |
| PB8 | Digital input returned as status byte 0 and used by commands `0x07`/`0x09` | Dispenser-door sensor; exact active polarity needs calibration |
| PA11/PA12 | Independent timed outputs selected by `0x0e` subcommands 1 and 2 | Upper and lower panel indicators |
| PA13 | Pulsed after a sampled state change; UART RX ends the pulse early | Electrical destination unknown |
| PB0 | Driven low immediately before the M0 enters WFI | Power-control effect, if any, is not established |

`sample_analog_channels` at `0x2d64` samples SARADC channels 6 and 7, sorts
each 20-sample buffer, and averages the middle ten values. Channel 6 is the
mains-adapter input and channel 7 is the battery input. For each channel, the
M0 reports the averaged ADC count and a centivolt value calculated as
`ADC × 3.3 / 4095 / 0.3197278911564626 × 100`. Live readings were
6.09 V for the adapter and 5.77 V for the unloaded battery pack on mains. On
battery power, the adapter changed to 0.00 V and the loaded battery pack to
5.14 V.

Live ESPHome diagnostics recorded an abrupt ESP8266 restart while M0 status
traffic was current and error-free. The ESP8266 then reported SDK reset reason
0 (`Power On`) and could not recover a valid RTC-memory checkpoint written
shortly beforehand. The ESP8266 Arduino core documents that SDK reason 0 can
also occur after some early hardware-watchdog and external resets. The earlier
firmware did not record the independent ROM reset source, so that event does
not establish which reset mechanism occurred. PA13 is relevant because the M0
pulses it after sensor changes, but its board destination must be traced before
treating it as a reset or wake signal.

The motor state machines use feedback, current/sensor thresholds, timeouts,
and explicit idle/brake output states. The ESP8266 requests operations, while
the M0 decides when to stop the motor and reports the result. More detailed
branch annotations will be added after each RAM field in the two motion state
machines has been correlated with captured completion payloads.

## Watchdog and reboot relevance

The routines at `0x34f4`, `0x351c`, and `0x34d8` configure, feed, and stop the
ISD91230 watchdog at `0x40004000`. That watchdog resets the Cortex-M0 itself;
the binary does not directly establish that it can reset the ESP8266.

The stock ESP8266 contains `MCU_HB error!! %d`, but the first recovered
reference is inside a configuration/event parser that updates two counters at
object offsets `0x210` and `0x214`; the string alone does not prove a periodic
M0 heartbeat check. The runtime consumer of those counters and its recovery
action still need to be recovered from the Xtensa image. The current ESPHome
implementation should therefore record the last valid M0 frame and the last
successful status reply, but it should not reset either processor until the
stock recovery behavior is understood.

## Remaining annotation work

- Name every unclassified application function and separate compiler/runtime
  helpers from device logic.
- Recover the exact PB1/PB2 and PB3/PB4 state-machine fields, limits, and
  completion error codes.
- Calibrate the PB8 dispenser-door sensor in the assembled feeder.
- Trace PA13 electrically or identify its corresponding ESP8266 GPIO behavior
